USSD / Admin LMS adapter — 27 October 2026

Status: private backend integration implemented; live operator journey incomplete.
The simulator remains separate. It has not been silently switched to real customers.
No changes to Admin LMS controllers, schema, existing tokens or production workflows.

Source modules:
  internal/lmsbridge — allowlisted HTTP adapter and encrypted request journal
  cmd/lmsbridge — private server, configuration and graceful shutdown
  deploy/mightyfin-ussd-lms.service — supervised single-instance runtime

Deployed service: mightyfin-ussd-lms.service (user systemd, enabled at boot)
Listener: http://127.0.0.1:28091
LMS upstream: https://admin.mightyfinance.co.zm/api/v1
Configuration: /home/mightyfin/.config/mightyfin/ussd-lms/runtime.env
Journal: /home/mightyfin/.local/share/mightyfin-ussd-lms/requests.enc
Service secret and journal encryption key are private files outside Git.
No public Caddy route is added. The simulator remains on localhost:28090.

Authentication:
Every adapter route except GET /healthz requires X-USSD-Service-Key. Customer routes
also require Authorization: Bearer <existing LMS customer token>. The adapter verifies
that token with LMS /users/profile and uses the resulting customer identity. Tokens
are never persisted. An unverified number or customer ID is not an identity credential.
LMS remains responsible for token audience, expiration, ownership and authorization.
The eventual gateway adapter must establish this trusted customer context; it must not
invent tokens or use the simulator's This is me button as live authentication.

Example quote body:
  {"loanProductId":7,"loanAmount":"1000.00","repaymentMonths":3}
Example draft body (use an actual LMS product, not demo salary/business IDs):
  {"loan_product_id":7,"amount":"1000.00","loan_term":3,"purpose":"Working capital"}
These IDs/amounts are syntax examples, not approved product terms.
Application requirements/validation come from LMS. Its submit endpoint currently
requires completed profile/documents; the adapter does not bypass that to imitate
the demo. Application/offer/balance/pricing logic is not duplicated in Go.

Write control and retry rules:
USSD_LMS_ENABLED=true starts the private service. Application mutations also require
USSD_LMS_WRITES_ENABLED=true; deployed value is false. A write needs Idempotency-Key
(1–80 ASCII letters/digits/underscore/hyphen). Keys are bound to the verified customer.
The journal reserves the key durably before the upstream request and stores the result
using AES-GCM, 0600 files, fsync and atomic rename. Identical completed requests replay;
changed requests with the same key return 409. Network errors, server errors, 408/429
and interrupted writes remain unresolved and must be reconciled, not resent blindly
with a new key. A 4xx validation result is also replayed; use a new key for corrected
input after confirming no write occurred. No automatic upstream retry is performed.
Secrets must remain private regular files; journal key is exactly 32 raw bytes.

Single-instance limitation:
The systemd unit uses flock and a dedicated directory. Always use this unit; never
start multiple independent processes against one journal. Capacity is 10,000 recorded
keys; reaching it fails closed. No automatic eviction is implemented, since losing
old keys would allow replay. Multi-instance rollout needs a transactional shared
idempotency store and a reviewed reconciliation/retention process.

Payments intentionally unavailable:
POST /v1/repayments returns ACTION_DISABLED in this deployment. Even enabling the
payments flag cannot activate it: the implementation returns 501 until the verified
collections adapter exists. The customer early-repayment endpoint posts a repayment
without initiating a provider collection and must not be used as a USSD payment rail.
The proper LMS integration collections service already handles initiation, verified
callbacks and posting. Its integration credential is not customer scoped. A narrowly
scoped customer-to-real-loan ownership adapter is needed before exposing it to USSD;
LoanResource can fall back from loan ID to application ID, so those IDs cannot simply
be treated as interchangeable. No broad integration credential has been provisioned.

Journey automation extension — 27 October 2026

GET /v1/journey (service key + LMS customer token) reads the current application and
customer-owned loans and returns state, next_action, missing_profile_fields,
missing_documents and a version of the current application snapshot. It does not
submit, run assessment, create an identity session, accept an offer or move funds.
A complete draft proposes review/confirmation; missing details propose continuation;
missing documents propose a handoff; pending/approved/rejected applications show LMS
status; an active loan proposes viewing repayment details. Unknown states, unknown
balances and unread loan pages do not propose another application. Document handoff
is marked unavailable until an actual secure handoff is integrated. Products shown
are available catalogue entries, not a promise of customer eligibility.

Submission now requires:
  X-USSD-Confirmation: submit
  X-USSD-Journey-Version: <version returned by GET /v1/journey>
  Idempotency-Key: <stable key for this confirmed request>
The adapter re-reads the current draft and rejects a changed snapshot, mismatched
application, or missing completion requirements. It then delegates submission to LMS,
which already queues ProcessLoanApplicationAssessment. No second assessment trigger
was added. The version comparison detects changes observed at re-read; it is not an
atomic compare-and-swap inside LMS across other channels. Production writes remain
disabled pending full end-to-end validation and concurrency handling at the LMS boundary.

POST /v1/identity/session delegates to the existing customer-scoped /didit/session,
with {"verificationType":"kyc"} or {"verificationType":"kyb"}. It requires
X-USSD-Confirmation: verify_identity, an LMS customer token, a service key, a stable
Idempotency-Key and application writes enabled. LMS resolves the appropriate provider
workflow; an already_verified result is preserved. Provider URL/status are returned,
not automatically sent by SMS. Retries replay the saved result and do not create more
provider sessions. Live Didit sessions were NOT created during verification. LMS
customer bearer tokens are not stored; the returned provider session result, if any,
is stored encrypted in the request journal.

Correction to the earlier KYC route list: GET /v1/kyc/status is now blocked (503).
Inspection showed that the deployed LMS GET /kyc/status calls syncApplicationAfterKyc,
which updates draft status/complete when documents exist. It cannot serve as a safe
read-only status check. The journey endpoint reads application_completion instead.
Document completeness is not equivalent to verified identity approval.

The deployed LMS API route inventory has Didit session/webhook support but no explicit
versioned customer offer-review/acceptance API. An approved application is therefore
NOT displayed as an offer ready to accept. That contract still needs implementation.

Verification: journey-state fixtures cover missing details/documents, complete drafts,
pending/approved status, active loans, unknown balances, pagination and inconsistent
completion. HTTP tests prove that journey reads never invoke the mutating legacy KYC
route or assessment POST. Submission tests cover absent confirmation, stale versions,
incomplete drafts and persistent idempotency. Identity-session tests cover explicit
confirmation and deduplication. Race tests and go vet passed. Real customer journeys
were not exercised; application writes/payment initiation remain disabled.

Phone status screens — 27 October 2026

GET /v1/journey/screen requires the same service key and LMS customer bearer token
as /v1/journey. It reads the same authoritative resources and returns JSON:
  text: short phone-friendly status, with "9 Refresh" and "0 Exit"
  state: LMS-derived journey state
  version: application snapshot version
  choices: [{"key":"9","action":"refresh"},{"key":"0","action":"exit"}]
The gateway must translate its wire protocol: refresh repeats this authenticated GET;
exit terminates the operator session locally. This endpoint does not accept menu input,
phone numbers, customer selectors or operator callbacks. No session is created here.
These are status screens, not a complete application/repayment menu. They currently
direct customers needing action to their officer. Even if writes are enabled, the
screen never offers submission, identity-session creation, acceptance or payment.

Each screen uses static ASCII text within 160 characters, including navigation.
That is a conservative internal budget, not a verified operator limit; actual gateway
encoding, prefixes, timeout and message limits must be checked before connecting it.
Raw LMS text, customer/application IDs, document names, provider URLs and tokens are
not copied into the screen. Responses are no-store. LMS failures remain errors and
are never converted into an empty account or an approval. The gateway must terminate
or show a generic retry message on non-200 responses, never display raw error bodies.

Tests cover all status-screen lengths and privacy, both authentication layers,
read-only repeated refreshes, rejected selectors/input/mutations, and upstream failure.
The operator protocol and real customer end-to-end journey remain untested. The local
simulator is unchanged and separate; no public Caddy route has been added.
