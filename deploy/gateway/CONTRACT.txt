Callback: https://ussd.mightyfinance.co.zm/ussd
Health: https://ussd.mightyfinance.co.zm/healthz

GET fields (case-insensitive, exactly one of each; duplicate aliases rejected):
  MSISDN       Trusted network caller: 260..., +260... or local 0-prefixed number.
  SESSION_ID   Unique per dial; 1–80 letters/digits/underscore/hyphen.
  INPUT        Initial dial: empty or up to 32 digits (e.g. 29).
               Continuation: latest answer only, at most 160 UTF-8 bytes.
  RequestType  1 initial dial; 2 each subsequent request.
URL-encode values: + as %2B, # as %23, * as %2A and spaces in names.
Unsupported fields, control characters, bodies and malformed encoding are rejected.

Access: Hobbiton gateway 41.175.8.68 via Cloudflare Tunnel is IP-allowed, with no
bearer header required. CF-Connecting-IP is accepted only from the loopback ingress;
CF-Worker, duplicate IP headers and untrusted peers are denied. Both Caddy (28092)
and app (28093) MUST remain loopback-only; local processes and zone administrators
are trusted. Never expose the origin ports or add an untrusted header-rewriting
proxy/Worker. Existing operator bearer credentials remain valid for diagnostics.

Responses: text/plain; charset=utf-8, Cache-Control no-store.
Bodies contain customer text only. No CON/END text is displayed.
FreeFlow: FC continues and accepts input; FreeFlow: FB ends the session.
Menus, Back/Main and menu refreshes use FC; terminal and error responses use FB.
Example body:
  Welcome to MightyFin
  1 Apply for a loan
  2 Repay a loan
  3 Get assistance
  4 Payment status

A name is used only from a uniquely matched existing LMS user record. Entering a
name as lead information does not authenticate or create an account. Unknown names
use Welcome to MightyFin. Existing borrowers see repayment first; an existing
application offers continuation assistance instead of another application.
* Previous and # Main are navigation commands. Numerical options are selectable.

Lead capture: consent -> existing/new real LMS lead -> active product -> requested
amount (or officer to advise) -> optional name -> confirmed follow-up. Source USSD,
status new, qualification pending, stable LEAD reference. Validated partial details
survive new sessions and gateway restarts. Existing open leads are reused; another
channel's source and qualified staff data are preserved. Lead capture creates no
user, PIN, OTP, wallet, credit approval or automatic conversion. See USSD-LEADS.txt.
Normal LMS registration/authentication/application completion rules are unchanged.

Repay: confirm caller's registered name (if available) and phone; 1 Confirm or
2 Enter phone number. An entered payment number is normalized and confirmed before
continuing. It selects the funding wallet. The borrower remains the trusted caller;
entering a number cannot reveal that number owner's private loan records.
The public flow does not implement arbitrary borrower-account lookup by typed phone.

After confirming the funding number, read the caller's loans from LMS. Use the
existing LoanAccountStateService for amounts due/outstanding; include only eligible
ZMW loans with positive outstanding balance and amount due. Zero/settled balances
are excluded even if legacy status is active. No match/no amounts due displays:
  You have no pending loan to pay back.
An ambiguous identity or service failure shows an assistance/unavailable response,
never a definitive no-loans message. Listing loans does not require a payment GL map.
Loan selections are numbered, three per page; 4 More and 5 Previous page appear as
needed. Up to 30 payable loans/history entries are supported; unusually large
accounts require assistance. Status history can include closed loans.

Select loan -> amount -> confirm selected loan, amount and funding number.
The private collection adapter rechecks ownership and the LMS outstanding balance
before new initiation. Amounts exceeding the remaining balance or newly cleared
dues return a balance-changed message without submitting a fresh collection.
The original borrower is used for ownership checks and the selected payer_phone for
the provider prompt. Use the existing LMS CollectionService/Gateway/RepaymentPoster;
provider/method is internally lipila/mobile_money. Customer wording is MightyFin.
After acceptance:
  Please wait for the payment prompt.
The response closes USSD with FB. Wallet PIN is entered only in the trusted mobile-
money provider prompt. Initiation remains pending/unknown until provider verification
and ledger posting; status never treats acknowledgement as paid. No provider brand
or wallet PIN field is shown by this USSD application.

Session controls: five-minute in-memory session; caller, protocol and authorization
context are bound. Re-entry is a new session; saved lead data and LMS financial
records persist. Initial/terminal duplicates replay. Active repeated digits can
represent a real next answer (1 then 1); without a gateway sequence ID, all network
retries cannot be distinguished from new answers. Financial confirmation differs
from a repeated one-digit amount; stable LMS keys and unresolved-collection guards
prevent duplicate prompts/postings. Keys include borrower, loan, amount and funding
phone. A timeout after initiation is processing, not proof of failure. Do not clear
pending records or create another attempt to work around uncertainty.

Private endpoints, loopback 28094:

  /v1/welcome,/v1/loans,/v1/status-loans,/v1/collect,/v1/status: payments:ussd
  phone is the borrower; optional payer_phone is funding-only for collect.
Never send these credentials to handsets. Do not log query strings, numbers, input
contents, provider PINs or service keys. Cloudflare/operator query retention must be
considered because GET carries contact/name inputs. The normalized funding phone is
kept in the short-lived session for confirmation and initiation, not in gateway logs.

Callback deadline four seconds including session-lock wait. Caddy upstream timeout
six seconds. Errors use 400/401/404/409/413/414/415/503 as appropriate. Non-200 is not a
financial outcome. Operators must still confirm network timeout, retry ordering,

Mighty Finance USSD callback — proposed contract v1

This contract is implemented for a payments pilot. It is our proposed interface,
not a claim that Hobbiton has supplied or accepted this format. Hobbiton can map
its gateway to this contract or send the differences for an adapter change.

Callback: https://ussd.mightyfinance.co.zm/ussd
Liveness: https://ussd.mightyfinance.co.zm/healthz
Method: POST
Content-Type: application/x-www-form-urlencoded
Authorization: Bearer <restricted operator pilot key>
User-Agent: MightyFinance-USSD-Pilot/1.0 (tested client identifier)

Exactly four form fields (all required, text may be empty):
  sessionId   Unique per dial attempt; 1–80 letters, digits, underscores or hyphens.
  phoneNumber Zambian international number, e.g. +260970000001 or 260970000001.
              URL-encode the plus sign as %2B; curl --data-urlencode does this.
  serviceCode Actual assigned dialling code; digits, * and #; at most 32 chars.
  text        Cumulative input separated by *, initially empty; at most 128 chars.
              Send one new selection each callback, e.g. empty -> 1 -> 1*9 -> 1*9*0.
              Menu choices are single ASCII digits; payment amount entry accepts up
              to seven integer digits and two decimal places. Whitespace, Unicode digits,
              control characters and empty intermediate selections are rejected.
No query parameters, JSON bodies, duplicate fields or extra fields are accepted.
Authorization, Content-Type and customer-token headers must not be duplicated.
Compressed bodies and non-UTF-8 charset declarations are not supported.
The example code *123# is illustrative and is NOT an assigned Mighty Finance code.

Example initial request (replace key and service code):
  curl --request POST 'https://ussd.mightyfinance.co.zm/ussd' \
    --header 'Authorization: Bearer <OPERATOR_PILOT_KEY>' \
    --header 'User-Agent: MightyFinance-USSD-Pilot/1.0' \
    --data-urlencode 'sessionId=pilot-unique-session-001' \
    --data-urlencode 'phoneNumber=+260970000001' \
    --data-urlencode 'serviceCode=*123#' \
    --data-urlencode 'text='

HTTP 200 response, Content-Type text/plain; charset=utf-8:
  CON Mighty Finance
  1 Loan products
  2 Application status
  3 Make payment
  4 Payment status
  0 Exit

CON means continue the session. END means terminate it. Do not display these
prefixes as menu content if your gateway uses them as control markers. Every
menu response fits our 160-GSM-unit budget including prefix/navigation (extension
characters count twice). Invalid control/non-GSM characters are not displayed; verify
that this matches Hobbiton's encoding and network limits.

Menu:
  1: live LMS product names, with no promise of eligibility. 9 returns to main menu.
  2: application status requires a separately authenticated LMS customer token.
     Without one the session ends with an officer/sign-in handoff message.
     With one, 9 refreshes status; 0 exits.
  3: select an eligible loan, enter a ZMW amount and explicitly confirm payment.
     Example cumulative path: 3 -> 3*1 -> 3*1*25.00 -> 3*1*25.00*1.
     0 cancels. The caller number is the payer; there is no alternative payer input.
  4: select a loan to check the latest payment on this USSD channel. Closed loans
     with payment history remain available for status checks.
  0: exit.
Invalid selections end the session. Product browsing remains informational.
The payment menu does not request a wallet PIN; authorization happens only in the
mobile-money provider prompt. No provider brand is displayed in customer messages.

Customer authorization:
The operator key authenticates Hobbiton's callback. Payment options 3/4 rely on
its operator-supplied subscriber number, not a customer PIN, OTP or token. The
private LMS payment module restricts loans to the uniquely matched phone account.
This requires Hobbiton to supply the trusted calling number and keep the operator
key private; a caller-typed number is not acceptable. Wallet debit authorization
is performed by the mobile-money provider. For application status (option 2), supply
X-LMS-Customer-Token: <valid existing LMS customer token> on EVERY callback,
including the initial one. LMS validates its audience, expiration and ownership.
Never put this token in text, a phone-number field, a URL, a screenshot or email.
A phone number alone is never used to impersonate an LMS account. Before reading
or replaying a customer status screen, the gateway validates the customer token
through /v1/me and compares its account phone with the callback subscriber number.
International (+260/260), local 0-prefixed and nine-digit account phone formats are
normalized; missing/mismatched phones end access without reading account status.
A failed authentication recheck removes earlier customer screens from that session.
This comparison is not proof of phone possession: Hobbiton's subscriber-number
provenance and callback authentication still require operator acceptance testing.
No customer token is included in the operator pack. Use a new session if the
authentication context changes. No PIN/password/OTP sign-in is required for the payment menu.
NRC is an identification/matching field only, never an authentication credential.

Sessions, retries and timing:
- Five-minute lifetime from first request; up to 2,000 sessions and 32 responses
  per session. State is memory-only, single process. Restart requires redial.
- Mobile number, service code and customer-token fingerprint are bound to the
  session; changing them returns HTTP 409. Session IDs must be unique per dial.
- Retry with exactly the same session and full text to replay the cached response.
  Do not retry using a new session ID for the same dial attempt.
- After END, the same END response may be retried, but earlier CON screens cannot
  be replayed to reopen the session; those requests return 409.
- Only one new selection per request. Skipping intermediate callbacks or branching
  from an earlier menu path returns 409. Fresh refresh input triggers a fresh read.
- Identical status retries first recheck the token and account phone, then replay
  the prior screen during the session lifetime. These are read-only snapshots,
  not authorization for any financial action. Ended sessions only replay END.
- Missing/expired sessions with nonempty text end with a redial message.
- Callback processing, including waiting behind another session request, has a
  4-second deadline. Cancelled queued callbacks return 503 and do not update the
  session. Expiry is checked again after acquiring the session guard.
  Cancellation/timeout during an upstream read returns 503 without consuming the
  selection or caching a terminal response for read-only account screens. Payment
  initiation timeouts instead return a processing message: an external request may
  already exist. Check payment status before starting another request. The durable
  LMS idempotency key protects an identical confirmation, including after timeout.
  Another unresolved collection on the same loan blocks a fresh payment prompt.
  Propose an operator timeout of at least
  8 seconds, subject to the operator's actual network budget.
- No request bodies, numbers, customer tokens or operator keys are logged by this
  application. In-memory rendered status is cleared when sessions expire/restart.

HTTP errors:
  400 malformed callback; 401 operator credential missing/invalid;
  404 unsupported path; 405 wrong method; 409 session identity/sequence conflict;
  413 body exceeds 8 KB; 415 wrong content type.
Infrastructure may return 502/503/504. Treat non-200 as failed callbacks; terminate
or show a generic temporary-unavailability message, never raw infrastructure text.
The adapter's upstream/customer failures produce an HTTP 200 END message without
account details. Do not interpret a health check as an end-to-end LMS readiness test.
Cloudflare rejected the default Python urllib User-Agent with HTTP 403/error 1010
during testing; the explicit client identifier above passed. Confirm the operator's
real HTTP client against Cloudflare before rollout. No zone security was disabled.

Health JSON explicitly reports:

Operator acceptance checklist:
1. Match this callback format or send the required differences.
2. Provision the assigned dialling code and route it to the callback URL.
3. Confirm headers/authentication, cumulative text, timeout and CON/END semantics.
4. Test initial menu, live products, Back, Exit, retry, expiry and failed auth.
5. Arrange separate authenticated-customer tests before any real customer rollout.

Loan repayment initiation and verification are connected to existing LMS collection
services. Applications, KYC, offers and disbursements remain separate work.
A real wallet prompt/debit and operator handset acceptance test remain required;
configuration readiness and mocked tests do not establish provider availability.
